# Benchmarks module — reproducible evidence for every measured claim

> **OPTIONAL module.** Install only when **the project makes quantitative or empirical claims it must stand behind** — any *measured number* about the system (latency, throughput, cost, accuracy, memory, conversion, error rate, …) that ends up in a commit, README, ADR, or released document. If the project never publishes a number, you do **not** need this module — the core `⚠ unverified` citation discipline already covers non-numeric claims.

## 1. What this adds

| Artifact | Path | Purpose |
|---|---|---|
| `benchmark_protocol_rule` | `.agents/rules/benchmark_protocol_rule.md` | `trigger: always_on` rule: every measured claim needs a reproducible page or carries `⚠ unverified <metric>` and cannot be cited. Defines the mandatory sections and the verdict discipline. Registers the `bench` branch type. |
| `run-benchmark` skill | `.claude/skills/run-benchmark/SKILL.md` | Human-gated (`disable-model-invocation: true`) flow: collect environment → snapshot commit → run the exact command → analyze → generate a reproducible chart → write the page. |
| Benchmark-page template | `{{project}}_wiki/benchmarks/_template.md` | The full page skeleton: frontmatter + all body sections in order, ending in an explicit verdict. |
| Frontmatter extension | appended into `{{project}}_wiki/_meta/conventions.md` | The `⚠ unverified <metric>` seal, the `benchmark` page type, and the portable `environment` block. See `conventions-extension.md`. |

It **complements** the core, it does not replace it. The core citation discipline (`⚠ unverified` = "no `file:line` yet") governs *technical* claims; this module adds an **empirical axis** (`⚠ unverified <metric>` = "a number with no reproducible page"). The two are independent — anchoring a `file:line` does not make a throughput number true, and a benchmarked number still needs its citation where it touches code.

## 2. Where benchmark docs live

```
{{project}}_wiki/
├── benchmarks/
│   ├── _template.md                  ← the page skeleton this module installs
│   ├── _index.md                     ← catalog of benchmark pages
│   ├── {work_id}.md                  ← one evidence page per measured claim
│   ├── {work_id}.csv                 ← raw data, versioned in git (never .gitignore'd)
│   └── {work_id}.{svg,png}           ← chart, generated by a committed script
└── ...
benchmarks/scripts/plot_{work_id}.{ext}   ← reproducible plotting script, in the project's language
```

- **`benchmarks/{work_id}.md`** — the evidence page. Self-auditing: its *exact command* plus its versioned artifacts must let a stranger who clones the repo reproduce the number.
- **Raw data + chart** live in git alongside the page. The page cites them; nobody regenerates a number from a screenshot.
- **The plotting script** is committed and re-runnable — the chart is never hand-made.

## 3. The rule in one paragraph

A measured number MUST be backed by a page under `benchmarks/`; without one it carries `⚠ unverified <metric>` and MUST NOT be cited. The page states a **frozen hypothesis**, an exact reproducible **setup** (versions + commit), a literally-runnable **command**, a **dataset** (with a fixed RNG seed where randomness exists, and a documented state-reset between runs), a **statistical method** that reports the interval/percentiles — the gate being statistical volume for the target CI, *not* a magic run count — **results** with a delta column and tail-outlier flags, versioned **artifacts**, an **analysis**, honest **threats to validity**, and an explicit **verdict**. Rates are measured by **wall-clock, not a derived `sum(latency) ÷ N`**.

## 4. Verdict discipline — the crown jewel

Every page ends with exactly one verdict, chosen from the **data**: `confirmed | refuted | partially-confirmed | inconclusive`.

- **Refutation is a valid, first-class result** — often the most interesting contribution a project makes. The original hypothesis is preserved and a *revised* one is documented; when the effect inverts the predicted direction, it is flagged **`refuted-with-sign-inversion`** (the a-priori model was conceptually wrong, not merely miscalibrated).
- The hypothesis is stated **once, before the run, and frozen**. Never retrofit it post-hoc to "confirm" it. Never re-run until a favorable number appears.
- **If the human appears to want a result dressed up** — hypothesis rewritten after the fact, the run repeated until it "works", a threat quietly dropped — **refuse and cite the anti-pattern** (`benchmark_protocol_rule.md` §7). This refusal is the point of the discipline.

## 5. Frontmatter this module standardizes

Real-world benchmark setups sprawl hardware/OS/version details inconsistently; this module pins one portable vocabulary. Appended to `{{project}}_wiki/_meta/conventions.md` (drop-in section in `conventions-extension.md`):

| Field | Values | Meaning |
|---|---|---|
| `type: benchmark` | — | The evidence page type; lives in `benchmarks/`, subject to `stale`. |
| `environment` | `cpu` / `ram` / `os` / `versions{runtime,toolchain,dependency}` | Portable generalization of hardware/OS/version blocks — the minimum to judge external validity and reproduce the run. |
| `parallelism` | `workers` / `per_worker` / `seed` | Optional — only for concurrent workloads; carries the RNG seed for determinism. |
| `⚠ unverified <metric>` | body seal | A quantitative claim with no reproducible page. Contrast base `⚠ unverified` = "no citation yet". |

## 6. Branch type registered

This module registers the ephemeral branch type **`bench`** with the core branching rule (`core/rules/git_branching_rule.md` §4.3):

```
bench/<work_id>__<scope>        (source: dev · PR target: dev · same approved-plan gate)
```

It is valid **only while this module is installed** — the core rule rejects `bench` otherwise (§9.8).

## 7. Install

See `INSTALL.md` §5-ter (benchmarks module). In short:

1. Copy `rules/benchmark_protocol_rule.md` → `.agents/rules/benchmark_protocol_rule.md`.
2. Copy `skills/run-benchmark/` → `.claude/skills/run-benchmark/`.
3. Copy `templates/benchmark-page.md` → `{{project}}_wiki/benchmarks/_template.md`.
4. Append `conventions-extension.md` into `{{project}}_wiki/_meta/conventions.md`.
5. Register `run-benchmark` in `.claude/skills/_index.md` (mark it manual-only).
6. Create `{{project}}_wiki/benchmarks/` and `benchmarks/scripts/` (with an empty `_index.md`).

Authored page content is written in **{{KNOWLEDGE_LANG}}**, like the rest of the wiki. Frontmatter keys/values, commands, and identifiers stay in English.

## 8. Opt-in escalations (NOT default)

The rule above is the **proven core** — a self-auditing page per measured claim, gated on human-run benchmarks. Heavier machinery is surfaced here but **not installed by default**; add it only when a concrete pain justifies it:

- **CI-gated benchmark regression.** Run the benchmark in CI and fail the build when a key metric regresses beyond a threshold vs. a committed baseline. *Escalate when:* a performance-sensitive metric silently drifts across merges and manual re-runs miss it. Until then, the `stale` mechanism (a `code_refs` change flags the page for a re-run) is enough.
- **Shared results dashboard / time-series store.** Push each run's raw data to a time-series store and chart the trend over releases, instead of per-page tables. *Escalate when:* the number of pages outgrows point-in-time comparison and you need the long-run trend. Until then, the per-page Re-runs table suffices.

Both are **not defaults**. Start with the proven core; add an escalation only when its triggering pain actually appears (the seed-vs-accretion principle — see `docs/design-rationale.md`).
