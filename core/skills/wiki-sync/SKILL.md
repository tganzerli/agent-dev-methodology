# Wiki Sync

Propagates an execution log from `{{project}}_wiki/work/executions/{work_id}.md` to the knowledge pages listed in its "Affected wiki pages" section.

**Mandatory human gate.** Do not run without an explicit invocation from the human (`disable-model-invocation: true` enforces this).

> **Language:** every page created or edited is authored in **{{KNOWLEDGE_LANG}}** (frontmatter keys/tokens stay English).

## Argument

`$ARGUMENTS` = the execution **file name** without `.md` (format `YYYY-MM-DD_slug`). It can differ from the frontmatter `work_id` (e.g. a `_step1` suffix); the file name wins. If not provided, ask.

## Token budget (read first)

This skill is expensive when done naively: `_meta/log.md` is append-only and grows without bound, and knowledge pages can run to hundreds of KB. Rules:

- ❌ **Never `Read`/`Edit` `{{project}}_wiki/_meta/log.md`.** `sync_bookkeeping.py` appends to it (step 4).
- ❌ Do not read the execution or a target page whole. Use windows: `grep -n '^#' file` to find the section, then `Read` with `offset`/`limit` on that section only.
- ✅ Have the `scribe` role (a cheaper model tier) draft the page text; the main thread only validates and writes.
- ✅ If the current session is already heavy, suggest `/clear` and re-invoking `/wiki-sync {work_id}` — everything the sync needs is in the execution on disk.

## Steps

### 1. Locate and validate the execution log

- `grep -n '^status:' {{project}}_wiki/work/executions/$ARGUMENTS.md` — confirm `status: done`. If `in_progress`, stop and ask the human to confirm (a premature sync can propagate incomplete state).
- `grep -n '^## ' {{project}}_wiki/work/executions/$ARGUMENTS.md`, then read **only** the "Affected wiki pages" section (plus any section it points to). If the section is missing, stop.

### 2. Draft the affected pages (delegated to `scribe`)

**Before dispatching**, validate the list — it goes stale: does every `UPDATE`/`APPEND` target exist (`ls`)? Is any `CREATE` already there (then it is an `UPDATE`)? Is each path still valid (renamed apps/modules)? Does the section say "None"? If the list is stale or empty, **stop and show the human** instead of syncing blind; a trio with no pages closes with the script alone (zero `--page`).

Ignore anything in the list that is not a knowledge page: `_meta/log.md` (the script appends it), `work/_index.md` (generated by `/work-index`) and the task.

For each remaining item, dispatch the `scribe` role (one per page, or one for a small batch) with: the action (`CREATE`/`UPDATE`/`APPEND`), the path, the execution excerpts that support it (with line numbers) and, for `UPDATE`, the **section** to edit (found via `grep -n '^#'`). It returns proposed text; it does not write. (Runtimes without sub-agents: draft inline, keeping the windowed reads.)

The main thread then:
- re-validates the `file:line` citations **by sampling** (`grep -n` / windowed `Read`) — at minimum every one backing a new or numeric claim; a claim with no reference becomes `⚠ unverified` for human review;
- writes: `(CREATE)` follows `.claude/skills/obsidian-markdown` + `{{project}}_wiki/_meta/conventions.md` §5; `(UPDATE)` is a **surgical** edit of that section (`mandatory_planning_rule.md` §3), never a page rewrite; `(APPEND)` adds to the end.

### 3. Update indexes

- `{{project}}_wiki/_meta/index.md` — add/update entries for the touched pages (use `grep -n` to find the spot; don't read the whole file needlessly).
- `{{project}}_wiki/work/_index.md` is **generated**; if the execution changed trio frontmatter, regenerate via `/work-index` rather than editing by hand.

### 4. Mechanical close-out (script)

One command updates the execution's `related[]`, appends to the central log, marks the plan `status: executed`, and runs the project's index-format guard if it has one:

```bash
python3 <skills-dir>/wiki-sync/sync_bookkeeping.py $ARGUMENTS \
  --page '{{project}}_wiki/domains/x.md|UPDATE|short note' \
  --page '{{project}}_wiki/services/y.md|CREATE'
```

`--dry-run` shows what it would do. It refuses an execution that is not `status: done`, an `UPDATE`/`APPEND` on a missing page and a `CREATE` of a page already in HEAD. Zero `--page` is accepted.
Written to `_meta/log.md`: `## [YYYY-MM-DD] wiki-sync | {work_id} | N pages touched` plus one line per page.

### 5. Report to the human

Show a concise summary:
- How many pages created / updated.
- List with wikilinks.
- Flag `⚠ unverified` claims that need human review.

### 6. Promote to the canonical branch — *(monorepo module only)*

If the **monorepo module** is installed and the sync ran on a per-app dev branch, **suggest** promoting the touched knowledge to the canonical branch so it does not fragment across branches:

```
✓ Wiki synced. The touched pages are in the knowledge layer and should
  reach the canonical branch. Next step: /promote-knowledge {work_id}
```

See `.agents/rules/knowledge_source_of_truth_rule.md` (installed by the monorepo module). **Single-repo projects have no second branch — skip this step.**

## Anti-patterns

- ❌ Syncing an `in_progress` execution without confirming.
- ❌ Touching pages not listed in the execution's "Affected wiki pages".
- ❌ Creating pages under `{{project}}_wiki/work/` during the sync (that is managed by the work-cycle, not by wiki-sync).
- ❌ Rewriting existing pages (always edit surgically).
- ❌ Adding a technical claim without a `file:line` citation.
- ❌ Hand-editing `{{project}}_wiki/work/_index.md` (it is generated — use `/work-index`).
- ❌ Reading/editing `_meta/log.md`, or reading the execution / a target page whole without need (see "Token budget").
